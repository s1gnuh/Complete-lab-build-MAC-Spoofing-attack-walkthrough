ATTACK

Ba kịch bản tấn côngThree attack scenarios

Chạy từng kịch bản khi chưa bật phòng thủ. Mở Wireshark trên Kali (card eth0) để quay lại bằng chứng.

Run each scenario with defenses off. Open Wireshark on Kali (eth0) to record the evidence.

Case 1MAC Spoofing — giả mạo danh tínhMAC Spoofing — identity impersonation

Attacker đổi MAC của mình thành MAC của victim để vượt qua lọc MAC / mạo danh.

The attacker changes its MAC to the victim's to bypass MAC filtering / impersonate it.

  1. Trên Kali, giả MAC của victim:On Kali, spoof the victim's MAC:
    kali — Case 1
    sudo ip link set eth0 down
sudo macchanger -m aa:bb:cc:00:00:10 eth0   # victim's MAC
sudo ip link set eth0 up
macchanger -s eth0                           # show current MAC
  2. Bằng chứng: gateway/switch giờ thấy hai cổng cùng một MAC; traffic đáng lẽ của victim có thể về attacker. Xem bảng MAC trên switch (bước Phòng thủ có lệnh fdb/show).Evidence: the gateway/switch now sees one MAC on two ports; traffic meant for the victim can reach the attacker. Inspect the switch MAC table (fdb/show in the Defense section).
  3. Khôi phục MAC thật khi xong: sudo macchanger -p eth0Restore the real MAC when done: sudo macchanger -p eth0

Case 2CAM Table Overflow — làm tràn bảng MACCAM Table Overflow — MAC flooding

Bơm hàng loạt MAC giả làm tràn CAM table, ép switch hoạt động như hub → attacker nghe lén được traffic của máy khác.

Flood the switch with fake MACs to overflow the CAM table, forcing it into hub mode → the attacker sniffs other hosts' traffic.

  1. Mở Wireshark trên Kali, lọc icmp. Trên victim, ping gateway liên tục: ping 192.168.10.1Open Wireshark on Kali, filter icmp. On the victim, ping the gateway continuously: ping 192.168.10.1
  2. Trên Kali, bơm MAC giả:On Kali, flood fake MACs:
    kali — Case 2
    sudo macof -i eth0        # Ctrl+C to stop after ~20s
  3. Bằng chứng: sau khi CAM tràn, Wireshark trên Kali bắt được gói ICMP giữa victim và gateway dù không gửi cho Kali. Chụp màn hình.Evidence: once the CAM table overflows, Wireshark on Kali captures ICMP packets between victim and gateway that were never addressed to Kali. Screenshot it.
Giới hạn cần biết: Open vSwitch có bảng MAC lớn và xử lý khác switch phần cứng, nên macof không chắc đẩy được OVS sang chế độ "hub" để nghe lén như Cisco thật. Nếu không bắt được traffic, hãy trình bày Case 2 ở mức minh họa khái niệm và dồn số liệu chính vào Case 1 & 3 (vốn chạy ổn định).Know this limit: Open vSwitch has a large MAC table and behaves differently from hardware switches, so macof may not push OVS into "hub" mode for sniffing the way real Cisco gear does. If you can't capture traffic, present Case 2 as a concept demo and base your main numbers on Case 1 & 3 (which are reliable).

Case 3ARP + MAC Spoofing — tấn công xen giữa (MITM)ARP + MAC Spoofing — man-in-the-middle

Attacker đầu độc ARP để đứng giữa victim ↔ gateway và đọc toàn bộ lưu lượng.

The attacker poisons ARP to sit between victim ↔ gateway and read all traffic.

  1. Trên Kali, bật chuyển tiếp để victim không mất mạng: sudo sysctl -w net.ipv4.ip_forward=1On Kali, enable forwarding so the victim keeps connectivity: sudo sysctl -w net.ipv4.ip_forward=1
  2. Chạy bettercap và đầu độc ARP:Run bettercap and poison ARP:
    kali — Case 3
    sudo bettercap -iface eth0
» set arp.spoof.targets 192.168.10.10
» set arp.spoof.fullduplex true
» arp.spoof on
» net.sniff on
  3. Bằng chứng: trên victim ip neigh cho thấy MAC của gateway (192.168.10.1) đã bị thay bằng MAC của Kali. bettercap in ra lưu lượng victim. Chụp cả hai.Evidence: on the victim, ip neigh shows the gateway's (192.168.10.1) MAC replaced by Kali's. bettercap prints the victim's traffic. Screenshot both.
  4. Dừng: trong bettercap gõ arp.spoof off rồi quit.Stop: in bettercap type arp.spoof off then quit.
DEFENSE

Cấu hình phòng thủ trên Open vSwitchConfigure defenses on Open vSwitch

Mở console của node Open vSwitch trong GNS3. Dùng OpenFlow rules để chặn — tương đương Port Security và Dynamic ARP Inspection của Cisco.

Open the Open vSwitch node console in GNS3. Use OpenFlow rules to block — the equivalent of Cisco Port Security and Dynamic ARP Inspection.

0 · Lấy số hiệu port thật (bắt buộc)0 · Get the real port numbers (required)

ovs — console
ovs-ofctl show br0        # list OpenFlow port numbers
Quan trọng: in_port=1/2/3 trong các rule dưới đây chỉ là ví dụ. Số port OpenFlow thật tùy thứ tự cắm cáp — xem cột đầu của ovs-ofctl show br0 rồi thay cho đúng, nếu không rule sẽ không khớp và phòng thủ không hoạt động.Important: in_port=1/2/3 in the rules below are only examples. The real OpenFlow port numbers depend on the wiring order — read the first column of ovs-ofctl show br0 and substitute them, or the rules won't match and the defense won't work.

A · Ràng buộc MAC ↔ port (chống Case 1 & 2)A · Bind MAC ↔ port (stops Case 1 & 2)

ovs — console
# allow only the correct MAC on each port, drop everything else
ovs-ofctl add-flow br0 "priority=100,in_port=1,dl_src=aa:bb:cc:00:00:50,actions=normal"
ovs-ofctl add-flow br0 "priority=100,in_port=2,dl_src=aa:bb:cc:00:00:10,actions=normal"
ovs-ofctl add-flow br0 "priority=100,in_port=3,dl_src=aa:bb:cc:00:00:01,actions=normal"
ovs-ofctl add-flow br0 "priority=10,actions=drop"
Kết quả mong đợi: khi attacker spoof MAC (Case 1) hoặc chạy macof (Case 2), frame bị drop ngay tại switch. Chạy lại Case 1/2 để xác nhận tấn công thất bại.Expected result: when the attacker spoofs a MAC (Case 1) or runs macof (Case 2), frames are dropped at the switch. Re-run Case 1/2 to confirm the attack fails.

B · Ràng buộc IP ↔ MAC cho ARP (chống Case 3)B · Bind IP ↔ MAC for ARP (stops Case 3)

ovs — console
# only ARP with correct IP-MAC pairs passes; others dropped
ovs-ofctl add-flow br0 "priority=200,arp,arp_spa=192.168.10.1,dl_src=aa:bb:cc:00:00:01,actions=normal"
ovs-ofctl add-flow br0 "priority=200,arp,arp_spa=192.168.10.10,dl_src=aa:bb:cc:00:00:10,actions=normal"
ovs-ofctl add-flow br0 "priority=200,arp,arp_spa=192.168.10.50,dl_src=aa:bb:cc:00:00:50,actions=normal"
# drop MUST be priority 150 (above the MAC rules at 100),
# else a spoofed ARP sent with a valid MAC slips through and the defense fails
ovs-ofctl add-flow br0 "priority=150,arp,actions=drop"

Lệnh kiểm tra & đặt lạiInspection & reset commands

ovs — console
ovs-appctl fdb/show br0        # view the MAC (CAM) table
ovs-ofctl dump-flows br0       # view rules + packet/drop counters
ovs-ofctl del-flows br0        # remove all rules (back to "no defense")
Cách so sánh: chạy mỗi Case 2 lần — lần 1 sau del-flows (không phòng thủ), lần 2 sau khi thêm rule (có phòng thủ). Số liệu lấy từ dump-flows (counter drop) và Wireshark.How to compare: run each Case twice — once after del-flows (no defense), once after adding rules (defense on). Pull numbers from dump-flows (drop counters) and Wireshark.

PACKET TRACER

Bổ trợ: cấu hình phòng thủ chuẩn CiscoSupplement: standard Cisco defense config

Packet Tracer dùng để minh họa cấu hình phòng thủ chuẩn doanh nghiệp (Port Security, DHCP Snooping, DAI) bằng lệnh Cisco IOS thật — rất hợp cho mục 3.5 so sánh và để vẽ sơ đồ đẹp. Lưu ý: PT không chạy được tool tấn công thật (macof, bettercap); nó chỉ mô phỏng khái niệm.

Use Packet Tracer to illustrate enterprise-standard defenses (Port Security, DHCP Snooping, DAI) with real Cisco IOS commands — ideal for the section 3.5 comparison and for clean diagrams. Note: PT cannot run real attack tools (macof, bettercap); it only simulates the concept.

1 · Dựng topology1 · Build the topology

  1. Kéo một Switch 2960 và 3 PC. Nối PC0→Fa0/1, PC1→Fa0/2, PC2→Fa0/3 bằng cáp Copper Straight-Through.Drag one 2960 switch and 3 PCs. Connect PC0→Fa0/1, PC1→Fa0/2, PC2→Fa0/3 with Copper Straight-Through cables.
  2. Đặt IP cho mỗi PC (cùng dải với lab): PC → Desktop → IP Configuration → 192.168.10.10 / .50 / .1, mask 255.255.255.0.Set each PC's IP (same range as the lab): PC → Desktop → IP Configuration → 192.168.10.10 / .50 / .1, mask 255.255.255.0.

2 · Port Security (chống Case 1 & 2)2 · Port Security (stops Case 1 & 2)

Click switch → tab CLI, gõ:

Click the switch → CLI tab, type:

switch — CLI
enable
configure terminal
interface range FastEthernet0/1 - 3
 switchport mode access
 switchport port-security
 switchport port-security maximum 1
 switchport port-security mac-address sticky
 switchport port-security violation shutdown
end
show port-security interface fa0/1   # verify
Kết quả: mỗi port chỉ chấp nhận 1 MAC. Nếu có MAC lạ (giả mạo/flood) → port vào trạng thái err-disabled (đèn đỏ).Result: each port accepts only one MAC. Any foreign MAC (spoof/flood) → the port goes err-disabled (red link).

3 · DHCP Snooping + DAI (chống Case 3)3 · DHCP Snooping + DAI (stops Case 3)

switch — CLI
enable
configure terminal
ip dhcp snooping
ip dhcp snooping vlan 1
ip arp inspection vlan 1
interface FastEthernet0/24
 ip dhcp snooping trust          # uplink to DHCP/gateway = trusted
 ip arp inspection trust
end
show ip arp inspection           # verify
Kết quả: ARP sai cặp IP-MAC (đầu độc ARP) bị loại trên các port untrusted — tương đương rule DAI đã làm trên OVS.Result: ARP with a wrong IP-MAC pair (ARP poisoning) is dropped on untrusted ports — the same idea as the DAI rules on OVS.
Lưu ý phiên bản: nhiều bản Packet Tracer không hỗ trợ ip dhcp snooping (mà DAI phụ thuộc vào nó). Nếu bản của bạn thiếu, hãy để phần demo DAI cho OVS và PT chỉ dùng cho Port Security (phần luôn chạy được); hoặc dùng ARP ACL cho host địa chỉ tĩnh thay cho snooping. Kiểm tra trên bản PT của bạn trước khi đưa vào báo cáo.Version note: many Packet Tracer builds do not support ip dhcp snooping (and DAI depends on it). If yours lacks it, keep the DAI demo in OVS and use PT only for Port Security (which always works), or use an ARP ACL for static-address hosts instead of snooping. Check your PT build before putting this in the report.

  2. Quan sát port tương ứng trên switch chuyển err-disabled; kiểm tra bằng show port-security. Chụp màn hình trước/sau cho báo cáo.Watch that switch port go err-disabled; check with show port-security. Screenshot before/after for the report.
